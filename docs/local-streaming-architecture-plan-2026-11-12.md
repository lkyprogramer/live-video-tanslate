# 本地日语实时中文字幕：架构改造与验证方案

日期：2026-11-12。核对基点：`77e24c3e490a11721041a40ad4bd203f51f84039`。同日评审修订见[第 13 节](#13-本次文档交付的验证状态)末尾。

**先验证架构，再决定是否换模型。** 主线是解开音频收包、语音活动检测、识别窗口、翻译提交和字幕显示之间的绑定。第一阶段固定 ReazonSpeech + Hy-MT2，只改变识别与提交调度；有收益后再加入可修订中文字幕。上下文、温度和词表分别对照，不与首阶段混测。

**状态：方案已形成，产品改造未实施。** 本次只核对源码、历史证据和本机 Reazon 时间戳能力，不宣称新链路已经改善质量、达到 1 秒出字或满足资源预算。视频和参考字幕由用户后续提供，本方案不包含搜集、下载视频或提取网站字幕的任务。

## 1. 范围与文档关系

### 本轮交付目标

- 纯本地处理标签页日语音频，输出简体中文字幕，保留原声。
- 优先减少边界导致的漏义与等待；同时控制草稿错误、改写频率和计算开销。
- 在相同音频上分别回答：滚动识别是否有效、句级提交是否有效、显示草稿是否有效。
- 无收益也是有效结论。失败时给出具体机制和证据，不靠继续扩大模型名单维持进度。

### 固定边界

- 不接云端 ASR、MT 或远程算力。不读取 YouTube 字幕轨，不做 OCR。
- 用户提供的参考字幕只进入离线评测，不进入运行时提示词、识别窗口或切句规则。
- 仅使用当时已经到达的音频。参考句末、未来 VAD 端点和整文件内容不能决定实时提交。
- 暂不引入第二个翻译模型、7B 定稿模型、同音纠错 LLM、新标点模型或 ASR 热词。
- 不要求先建 200 项新数据集。人工参考修正与工程验证并行；未经复听的参考保持待确认。
- 当前默认 `reazon-hy` 保留。实现、提交、推送、发布各自按实际授权推进，本次请求仅交付文档。

### 对旧计划的处理

本方案是下一轮**架构实验的主入口**。旧 P2/P3 的结果仍按原配置、原评分规则成立，不重新解释成新架构结果。

实验机上的 `docs/live-video-translate-p3-2026-11-10/` 是未跟踪目录，不在仓库中，读者无法从仓库核对其内容；下述对它的描述只来自实验机本地文件。该包以新模型筛选为主，且规定 provisional 日文不进入 MT、对外中文不可回写。本方案将模型筛选后移，并为草稿设计新协议；这些是**拟议合同变更**，尚未改变现行 [v1 合同](subtitle-backend-contract.md)。旧包不作为执行本方案的必要依赖，也不修改它的清单或历史回执。

### Reazon 时间戳：本次新增实测

本机 `sherpa-onnx==2.0.1`、现有 Reazon 权重、CPU 2 线程，无升级、无新模型下载。对已有 `first-photo.pcm` 做整段、前半段和静音探针，结果见 [可共享摘要](experiments/architecture-2026-11-12/timestamp-probe-summary.json)。

| 输入 | token 数 / 时间戳数 | 时间范围检查 | token durations |
| --- | ---: | --- | --- |
| 7 秒完整音频 | 22 / 22 | 单调非递减，位于输入范围内 | 空 |
| 前 3.5 秒 | 4 / 4 | 单调非递减，位于输入范围内 | 空 |
| 1 秒零值，直接调用 ASR | 2 / 2 | 单调非递减，位于输入范围内 | 空 |

结论是：**底层离线结果提供 `tokens` 和 `timestamps`，当前业务封装仅返回 `text`。** “业务接口仅返回文本”成立，“离线模型没有时间戳”不成立。上游 [transducer 转换源码](https://github.com/k2-fsa/sherpa-onnx/blob/master/sherpa-onnx/csrc/offline-recognizer-transducer-impl.h)也展示了 token 时间值换算；该链接是可变的上游源码，本机能力以本次探针与固定依赖为准。

同一前缀随输入增长，两个对应 token 的时间戳分别变化约 120 ms、80 ms，首 token 还落在 0。时间戳不是已经校准的词尾，更不是跨窗口永不变化的裁音点。不要沿用 PengCheng 在线分支中的“末 token 加 40 ms”假设来裁 Reazon 音频。

静音探针直接返回 `えっ`。这是**绕过 VAD 的裸 ASR 行为**，不推翻 B0 的 VAD 端到端静音零字幕结果；它说明滚动识别仍需语音活动门控。此探针没有验证时间戳的语音对齐精度、完整长句、重叠裁切或实际 Chrome 效果。

## 3. 目标链路与状态归属

```mermaid
flowchart LR
    A[Chrome 标签页音频] --> B[200 ms PCM 收包与采样时钟]
    B --> C[有界音频缓冲]
    B --> V[VAD 语音活动与停顿提示]
    C --> R[现有 Reazon 滚动离线重解码]
    V --> R
    R --> S[日文假设对齐与句级提交]
    V --> S
    S --> Q[合并草稿任务并优先处理定稿]
    Q --> M[同一个 Hy-MT2]
    M --> G[版本与会话校验]
    G --> U[中文字幕草稿与定稿]
```

Reazon 仍是离线识别器。这里的“滚动”指在已到达音频上重复解码有界窗口，不声称它获得了原生流式缓存或增量 encoder。

| 边界 / 状态 | 负责内容 | 不再承担的职责 |
| --- | --- | --- |
| PCM 包 | 传输、样本计数、背压；固定 16 kHz 单声道 s16le、200 ms | 不决定一句话的起止 |
| VAD | 是否有语音、起点、停顿、静音控制 | 不强制把每次 4 秒释放都当成独立句子 |
| ASR 窗口 | 只重算已到达的有限音频；保存窗口起点和解码水位 | 不直接创建最终中文 |
| 日文假设 | 保留 token、时间锚点、稳定部分、可变尾部 | token 稳定不等于句意完整 |
| 句级提交 | 冻结这次 MT 的源文范围，记录自然结束或强制边界 | 不判断中文是否翻译正确 |
| MT 调度 | 串行推理、合并过时草稿、保护定稿、丢弃旧结果 | 不积累每个 ASR 快照的独立翻译队列 |
| 字幕行 | 一行身份、修订与最终状态；前端按行更新 | 不再用单个 `seq` 同时代表行身份和事件身份 |

状态优先留在现有 `LocalSession` 生命周期内。无需先建通用流处理框架、插件系统或分布式队列。识别对齐和字幕事件可用明确的数据类型表示，其余逻辑按真实职责放入现有实现；测试确需隔离时再提取小模块。

音频至少区分 `accepted_samples`、`consumed_samples` 和当前解码快照的 `decoded_through_sample`。后台解码期间新到达的音频可以进入缓冲，但不能被该次结果声称已识别。补零不推进真实样本时钟。

**背压必须重新定义。** 现有 `overloaded` 依赖网关逐帧 `await session.accept_pcm(frame)`：识别阻塞时网关的 64,000 样本队列才会填满（[app.py](../engine/src/subtitle_service/app.py) 的 `process`）。`accept_pcm` 一旦改为只入缓冲，这个触发点失效，过载会变成无界滞后。滚动后端自己负责上限：`consumed_samples − decoded_through_sample` 在语音活动期间超过第 4.2 节的滞后上限即报 `overloaded` 并结束会话，不静默丢音频。

现有 VAD 与识别共用单线程 `asr_pool`。滚动解码若留在同一线程，一次长窗口解码会推迟 VAD 对后续帧的处理。实现时二选一并写入 A0 记录：VAD 移到独立的轻量执行位置，或保留共用线程并把 VAD 延迟计入停顿确认的实测等待。

## 4. 第一阶段：滚动识别与句级提交

### 4.1 固定项与实验拆分

固定现有模型 revision、精度、CPU provider、2 线程、Silero v4 权重、600 ms 静音阈值、Hy-MT2 1.8B 4bit、提示模板和采样配置。

**实际基线温度是 0.2。** 本机 B0 的 `mt-settings.json` 和当前安装的 WhisperLiveKit 配置均为 `temp=0.2, top_p=0.9, top_k=20, repetition_penalty=1.1, max_tokens=512`。不把模型官方推荐值替换成本机基线。A0 执行时再次导出实际生效值；漂移则先说明。

| 配置 | 变化 | 要回答的问题 |
| --- | --- | --- |
| B0-new | 当前生产链路，同批材料、同轮重跑 | 本轮控制是否可复现 |
| A1a | 滚动识别，仍按当前 VAD 放行边界提交；只发定稿 | 等价性与不变量关卡：裁切、对齐、去重是否不丢不重，日文和最终中文是否不劣于 B0-new；记录滚动解码成本 |
| A1b | A1a 基础上解除 VAD 片与 MT 单元的一一绑定；只发定稿 | 句级提交是否改善语义或等待 |

A1a 的边界按实时 VAD 产生，不能把离线已经知道的全部端点提前注入。A1b 同时相对 A1a 和 B0-new 比较，避免两个调度变化互相掩盖。

**A1 的延迟预期要写实。** A1a 仍在 VAD 放行点提交且只发定稿，B0 的 ASR 计算 P95 只有约 150 ms，没有可省的“提前计算”，定稿延迟预期与 B0 持平。A1b 保留 600 ms 停顿确认，自然边界的定稿延迟与 B0 相同，等待更长单元时反而更晚；只有句末标点提前提交能让定稿变早，而该路径是否存在取决于 A0 的标点计数。A1 的可能收益主要是语义质量，面向用户的延迟收益只能来自第二阶段草稿。

**先离线因果模拟，再改产品代码。** 给定 PCM 到达顺序，滚动、对齐与提交逻辑是确定性的。A1a/A1b 先在 `p0/` 下用 9 段 PCM 按 200 ms 到达顺序离线模拟，只使用当时已到达的音频，产出日文单元和两轮 MT 结果；解码耗时单独实测后叠加到模拟时钟。离线结果达到第 9 节继续条件后，才把同一逻辑接入 `local_pipeline.py` 做真实 1× 对照。离线无收益即在此退出，不进入服务改造。

### 4.2 初始参数

下面是首配置的工程起点，不是实测最优值。第一轮冻结后不根据单个样本反复改参。

| 参数 | 起点 | 理由与验证方式 |
| --- | --- | --- |
| 收包间隔 | 200 ms | 保留现有传输合同 |
| 滚动解码间隔 | 800 ms | 先量重复解码成本；400 ms 仅在有资源余量和等待证据时追加 |
| 同时进行的 ASR | 1 次 | 避免同一模型并行重算与队列增长 |
| 待执行 ASR 快照 | 至多 1 个、始终指向最新水位 | 忙时合并触发，不丢 PCM、不逐 tick 排队 |
| 稳定候选 | 两次连续有效解码一致的未提交 token 前缀 | 必须有新增音频；同一窗口重复解码两遍不算两次支持 |
| 可变尾部保护 | 至少保留最近 400 ms 对应 token | 降低窗口右缘不稳定影响；不能单独作为最终提交条件 |
| 左侧重叠上下文 | 800 ms | 初始值；配合 token 对齐验证，不凭文本长度裁音 |
| 单次解码音频上限 | 12 秒 | 包含左重叠及尚未提交内容，避免无界重算 |
| 未提交音频软上限 / 硬上限 | 6 秒 / 10 秒 | 从该单元起点计 PCM 时长，含短停顿；软上限寻找边界，硬上限必须明确提交或失败 |
| 停顿确认 | 600 ms | 先保留当前等待，不同时扫 VAD 参数 |
| 解码滞后上限 | 4 秒 | `consumed_samples − decoded_through_sample` 的会话内上限，与现有 64,000 样本队列同量级；超过即 `overloaded` |

“最新快照”只有调度意义，不能使较早的句末提交任务消失。句末和 EOF 的解码屏障优先于普通滚动 tick，必须覆盖应提交的源文范围。

单次解码耗时随窗口长度增长。B0 的 150 ms 是较短 VAD 切片上的 P95，12 秒窗口的耗时没有实测；A0 先量 4、8、12 秒窗口的单次解码耗时，若接近或超过 800 ms 间隔，先缩小窗口上限，不靠合并 tick 掩盖。EOF 后的 8 秒 drain 预算要覆盖一次尾部解码、至多 4 条待译定稿和 1 条在途翻译，A0 用实测耗时核算，超出则降低定稿队列上限。

### 4.3 语音门控与句子边界

1. PCM 连续入有界缓冲，静音也推进时钟。VAD 使用现有权重、阈值与输入粒度，输出活动状态和停顿线索。
2. 语音活动开始后才启用周期性重解码，保留必要的前导音频。活动结束后做一次尾部解码，然后停止静音期间的无效重算；不把静音误识别送入 MT。
3. 区分自然停顿、VAD 最长段释放和 EOF。4 秒最长段释放只能是管理信号，不能自动成为句末。A0 必须核对本机 VAD 能否直接提供足够信息；不能提供时，在适配层依据活动状态与已到达音频记录原因，不猜测释放原因。
4. 最早的自然提交候选是稳定前缀中的已有句末标点，并且右缘保护和时间对齐通过。Reazon 原始输出的句末标点很可能稀少（见第 2 节），此规则不能是唯一出口，也不新增标点模型。A0 计数显示标点率过低时删除本规则，方案退化为停顿提交加长度上限，并按该形态评估。
5. 600 ms 停顿触发尾部重解码，并以已到达音频确认该段。标点前缀之外，停顿是主要的实际句界线索。由语气、助词或词尾做的简易猜测不被包装成语义解析器。
6. 到 6 秒尚无句界时，只记录等待并寻找已观察到的稳定候选；不能为了满足计时强截任意字符。到 10 秒时执行一次最终快照，按可校验的稳定范围提交，记录 `boundary_reason=forced_limit`。
7. 若硬上限时仍没有可靠的部分对齐，允许将本次完整未提交范围作为有界单元做一次性结束解码，明确记录 `forced_unstable`。它不宣称是完整句，也不宣称稳定。无法排除与已提交范围重复或缺失时，报告 `adapter_unaligned` 并结束本次实验会话，不静默丢音频继续运行。
8. EOF 提交剩余真实音频，并记录 `boundary_reason=eof`。空源文不翻译，草稿不能不经最终状态处理就随 `finished` 消失。

“final”只表示此行后续不再修改，不表示系统已经证明译文正确。自然边界、强制长度边界和 EOF 要分别统计质量、延迟及占比。

### 4.4 对齐、重复与缓冲回收

识别结果增加窗口起点、实际解码末点、原始 token 与相对时间戳。换算为绝对样本锚点时使用 `window_start_sample + round(timestamp_s * 16000)`；不得用 `.strip()` 后的字符位置反推 token 位置。

稳定性比较先在同一音频重叠区对齐 token，再比较未提交部分。文字规范化只做已验证的 tokenizer 还原；不能忽略否定、数字或反复出现的同一个词。首 token 的 0 时间值、同时间 token、时间漂移均需保留在诊断中。

先推进**逻辑已提交位置**，再在其左侧保留重叠音频。物理回收不直接取“末 token 时刻 + 固定 40 ms”；应结合下一个未提交 token 的锚点或已确认停顿，保留保护区。重叠区仅用于识别上下文，不能再次翻译已提交 token。

跨窗口只在对应时间区域做序列对齐。禁止全局替换重复字符串：说话者真的重复“はい、はい”必须保留。对齐不明确时暂缓移动窗口；到达硬上限按上一节的有界路径处理。

A0/A1 的必要用例是：边界跨词、重复词、句末否定、数字/专名、无停顿长语音、VAD 强制释放、短尾帧、EOF、长静音及音乐。只有时间戳字段存在，不构成裁音验收通过。

## 5. 第二阶段：同一 Hy-MT2 的草稿与定稿

在 A1 验证完成之前，不实施完整的浏览器草稿功能。若 A1 只证明可靠日文更早出现、最终中文尚未改善，则先做小范围 MT 草稿探针，确认正确中文确实提前，再进入协议与 UI 接入。

### 源文和中文的不同状态

内部源文可以是可变假设、稳定候选或已提交单元。显示状态只有中文草稿、中文定稿及撤回。稳定的日文前缀可以触发草稿，但不能直接触发中文定稿。

翻译总是对当前行的完整源文快照进行；不把新日文后缀单独翻译再拼接旧中文。日语句尾到达后，中文语序和否定可能整体改变。

### 调度规则

- 单个 Hy-MT2 常驻，仍只允许一个 MT 推理在途。
- 当前开放行最多保留一个待译草稿，后来的版本替换旧的待译版本；初始草稿提交间隔不小于 800 ms，文字未变不提交。
- 定稿队列最多 4 个待译单元，另有一个在途任务。定稿优先于尚未开始的草稿；有定稿积压时不新增草稿推理。
- 不能假设取消 asyncio future 就终止了底层推理。在途草稿完成后校验会话、行、源文版本与配置指纹；过时结果丢弃，并记录已发生的成本。
- 草稿无效时不覆盖已显示的有效内容；若行最终无有效译文，撤回这行草稿并报告 `translation_invalid`，不能把旧草稿留成看似定稿。
- 源文提交后才请求对应 final。若最近草稿的源文、提示、上下文、采样设置及种子均与 final 完全一致，可复用结果，只发送最终状态；不能只凭中文相同推断源文相同。
- 一行 final 后不可改写。之后发现的 ASR 修正记录为诊断或影响下一行，不回填已定稿内容。
- 保留现有中文过滤、背压和 8 秒 drain 限制。超时不把草稿强制改名为正确定稿；明确标记失败并清理。

### 防止草稿改变对照组的随机采样

实验期间为每个源文行固定种子映射，草稿修订与该行 final 使用相同的行种子；每次调用在同一个串行 MT 执行线程中设置种子。这样插入草稿调用不会消耗后续 final 的随机序列而污染 A2 对照。先验证相同 final 输入在“仅定稿”和“草稿＋定稿”两种调度下逐字一致。

不同切句方案的行数和输入长度会变，不能声称相同 seed 已消除全部随机差异。两轮 seed 11/29 分开报告，不能累计为 68 个独立语义样本。线上正常使用是否保留固定行种子在实施时明确，不能将实验控制误写成当前线上行为。

## 6. 字幕 v2 协议与显示

### 兼容策略

在现有 `WS /v1/captions` 路径上用 `start.version=2` 协商 v2，沿用现有 loopback、Host、Origin、token、音频格式和生命周期约束；路径中的 `v1` 作为历史端点名保留。`version=1` 的会话保持现有只发一次的 final 行为。

不另开 `/v2/captions` 的原因是版本发现：旧服务没有该路由，WS 升级直接失败，扩展无法与“服务未启动”区分；而旧服务对 `version≠1` 已返回 `unsupported_version` 并以 4400 关闭（[app.py](../engine/src/subtitle_service/app.py) 的握手校验），天然给出明确错误。扩展当前没有该错误码的文案（[protocol.ts](../extension/src/protocol.ts) 的 `messages`），实施时补上。若实现时仍决定使用独立路径，必须先在 `/v1/profiles` 或 `/v1/health` 增加协议版本发现，否则“明确提示版本不匹配”无法兑现。

新服务同时保留 v1；新实验扩展与 v2 服务成套验证。旧客户端继续走 v1。v2 网关可以把现有 final-only 后端结果投影为单版本 final 行，用于对照。新滚动后端若暴露给 v1，必须只投影 final；禁止把草稿塞进 v1 的 `caption`。

候选使用明确的实验配置，例如 `reazon-hy-rolling`，默认配置仍是 `reazon-hy`。不自动把旧后端切成新调度。旧服务不支持 v2 时明确提示版本不匹配，不在一次会话中悄悄降级协议。回滚使用经过验证的原扩展与原配置。

### 事件模型

以下是拟议 v2 事件示例，尚未加入现有 Schema：

```jsonl
{"type":"caption","session_id":"s-1","seq":1,"line_id":1,"revision":1,"state":"draft","start_sample":16000,"end_sample":48000,"text_zh":"我认识这些人。"}
{"type":"caption","session_id":"s-1","seq":2,"line_id":1,"revision":2,"state":"final","start_sample":16000,"end_sample":64000,"text_zh":"这些人中有很多我不认识。"}
{"type":"caption","session_id":"s-1","seq":3,"line_id":2,"revision":1,"state":"draft","start_sample":64000,"end_sample":80000,"text_zh":"接下来……"}
{"type":"caption","session_id":"s-1","seq":4,"line_id":2,"revision":2,"state":"withdrawn","start_sample":64000,"end_sample":80000}
```

第一行到第二行刻意展示草稿可能发生的否定翻转。它应计入草稿关键错误，不能因为 final 正确就从统计中删除。

| 字段 | 约束 |
| --- | --- |
| `session_id` | 绑定连接；前端还要匹配当前 activation/epoch |
| `seq` | 每个字幕变更事件严格递增；用于接收去重，不是行身份 |
| `line_id` | 会话内按源文顺序分配的正整数，行被撤回后也不复用 |
| `revision` | 同行每个已发送版本递增，从 1 开始；内部被合并的 ASR 版本另行记录 |
| `state` | `draft` 可更新；`final` 与 `withdrawn` 为终态；允许直接发送 final |
| `text_zh` | draft/final 必须有有效中文；withdrawn 不携带文字 |
| 样本范围 | 位于真实已接纳且本次已解码范围内；draft 范围可以随修订收缩或扩张；final 冻结 |

v2 不沿用 v1 对**所有字幕事件**的 `end_sample` 全局非递减约束：同一行的 draft 范围可以随修订收缩。改为校验行顺序、每行范围及终态的源文边界；不同 final 行不重复消费已提交源文，终态事件的 `end_sample` 跨行非递减。v1 的原校验保持不变。

第 5 节的调度（单个 MT 在途、定稿优先、有定稿积压不新增草稿）推出一条线上不变量：**同一时刻至多一行处于非终态，`line_id = N+1` 的首个事件一定晚于行 N 的终态事件。** 网关按此校验，`seq` 与 `line_id` 因而同向递增；违反即按适配器错误处理，不为跨行乱序设计兼容逻辑。以后若放宽调度使两行同时开放，需要先修改本节。

无需为正常 WS 有序传输构建复杂重排系统，但必须拒绝旧会话、旧 revision、终态后的更新、上一行未终态时的新行事件和越界时间。网关与扩展共用 v2 fixture；不能只改 TypeScript 类型而遗漏 Python 校验或 JSON Schema。

### UI 行为

- 最多显示上一条定稿和当前草稿两行，使用固定行位，草稿做轻量视觉区分。
- 新 revision 更新原行；不追加为新字幕，不重置另一行的停留计时。
- 按上述不变量，当前行进入终态后才会出现下一行；前端收到已终态行的事件或跳行事件一律丢弃。withdrawn 删除对应草稿。
- final 的可读停留要求沿用 `max(0.6 秒, 非标点字数 / 12)` 的测量口径；若快速语音使两行容量不足，记录真实覆盖损失，不声称全部可读。
- 只有状态变 final、文字未变时，测量上的可见区间可以连续；文字发生变化则重新计算该版本的连续可见时间。
- 暂停、seek、换源、断连及关闭沿用 epoch 失效和清空机制；旧计时器不得清除新行。
- 生产 UI 不展示 token 稳定性、窗口水位、参数名等实现细节。

## 7. 评测与因果对照

### 材料与参考

现有 9 段 PCM、34 项必要语义用作开发回归。15 个待复听项继续标注待确认；`wmf-04/153-155` 的原 119.60 秒与候选 126.04 秒不能未经听审就选择后者。

用户提供新视频和字幕后，登记内容哈希、来源、采样格式及字幕性质。字幕是源转写、人工翻译还是自动字幕需要区分；字幕时间不自动等于实际语音句末。先划分开发片段和未用于选参的保留片段，再做人工语义与时间校准。新材料数量以实际内容覆盖为准，不凭空承诺达到某个分母。

同一批新参考必须同时重评 B0-new 和候选。旧评分和修订评分分开保存；不能把修正参考带来的提分记成架构收益。材料尚未提供时，可以完成 mock、协议和已有素材的工程验证，新内容质量与泛化结论保持 `NOT_RUN`。

### 必报指标

| 指标 | 定义与防止误读的规则 |
| --- | --- |
| final 正确覆盖 | 全部必要语义项中，最终中文完整传达的比例；错误、缺失、部分正确、待确认分列 |
| 恢复 / 回退 / 净变化 | 相对同轮 B0-new 逐项配对；不只报总分 |
| 新增关键错误 | 主体、否定、数字、时间、核心对象或关系发生错误；草稿和 final 分开记录 |
| 首次任意中文 | 只作功能时刻，不代替首次正确 |
| 首次正确草稿 / 任意状态正确中文 | 完整必要语义首次出现的时刻；另报是否达到连续可读时长 |
| 持续正确中文 | 首次满足可读时长、且之后未被错误修订推翻的正确版本；后续退错不能被提前一次正确掩盖 |
| final 延迟 | 参考真实语音句末到 final 可见；final 必须正确才计入“正确 final 延迟” |
| 5 秒正确可读覆盖 | 固定全体分母，以 DOM 可读版本判定；草稿与最终覆盖分别给出 |
| 修订负担 | 每行可见文本变更次数、字符编辑比例、撤回次数、方向性翻转、错误草稿暴露时长 |
| 提交与调度成本 | ASR 次数、累计重解码音频秒、强制边界占比、草稿合并/废弃次数、MT 调用数、定稿等待 |

WS 与 DOM 指标分别列，诊断中记录实际 `line_id + revision`。没有真实浏览器记录时不得称 DOM 延迟。

短暂闪现的正确内容单列，不算正确可读覆盖。延迟原值保留负数以表示提前，展示时可另列 `max(0, delay)`，不能删除提前量。未正确项保留全体分母；共同正确项的配对 P50/P95 只能说明这些项，不能隐藏候选新增缺失。

少量样本的 P95 可能就是最大值，必须给出样本数、排序值与未命中数。按视频分组看方向一致性；不把两个种子或相邻语义项当作独立扩样，不声称小样本证明统计显著。

### 分离识别、边界与翻译的责任

先比较 ASR 是否保存必要日文信息，再比较同源文下的 MT。为定位 MT 可以用人工校正源文替换 ASR 字符，但保持候选实际边界；若还使用人工整句边界，必须单列为另一个诊断条件。不能再次把同时换字、换句界、加上下文的结果称为纯 MT 上限。

重复运行采用 seed 11/29 两轮；B0-new、A1a、A1b 同材料同轮运行，结果顺序交错或轮换以减少机器热态影响。无需做大规模统计试验，但不能挑较弱的历史控制作为基线。

## 8. 资源、实时性和 Chrome 采音对照

### 资源测量

复用 [P2 资源采样](../p0/p2/resources.py)、[原速回放](../p0/p2/realtime.py)和已有事件记录，补充滚动窗口与修订事件。现有 P2 CLI 没有本方案 A1/A2 的执行分支，需要按实施阶段补入口；不能只改实验名就声称已支持。

- 1× 联跑 ASR、MT、播放与采样；离线 RTF 只用于机制诊断。
- 分列服务进程树和 Chrome＋服务完整进程树。CPU 100% 表示一个核，报告均值、P95、CPU 秒/音频秒及同轮差值。
- 继续记录完整树 physical footprint、RSS、全机 GPU、共享内存、压力与交换。重叠指标不相加，峰值不相减后声称模型独占占用。
- 保留 2.5 GiB 作为默认低占用资格目标：正式 Chrome 比较在预先冻结的同一完整进程树范围内测热态峰值。B0 的 Chrome 完整字幕组峰值已是 2168 MiB，余量约 390 MiB；滚动音频缓冲本身很小，余量主要留给解码与 MT 的峰值变化。服务单跑低于该值不等于浏览器联跑合格；超标可以完成实验，但不自动替换默认。
- 当前约 9.5% CPU 只适用于历史无 Chrome 的原速控制；不沿用为滚动解码预期。CPU 是滚动解码的主要成本：A0 量出单次解码耗时后、A1 结果揭示前，写下服务进程树 CPU 均值与 P95 的可接受上限。CPU 开销明显上升时报告对应收益，不事后把预算写成刚好通过的值。
- 滚动 tick 被合并、队列年龄持续增长、drain 超时或持续过载均计入结果。不能以静默丢音频或跳过 final 换取实时性。

现有样本队列上限 64,000 samples、入队等待 1 秒、浏览器 `bufferedAmount` 上限 64,000 bytes 和单会话占用规则保持。已消费的重解码缓冲与尚未消费的 PCM 队列是两种内存，分别计上限，不能以“已有队列上限”声称滚动缓冲天然有界。

### Chrome 采音对照，可与 A1 独立进行

历史同片段原 PCM 为 4/8、真实捕获为 3/8，ASR 已有短发信息丢失，说明输入路径值得核对，但尚未定位到 AAC、重采样或 VAD。

对用户后续提供的同一视频分别保存本地解码到 16 kHz 的控制 PCM，以及实际 tabCapture→Worklet 的 PCM。对齐共同时间区域，检查缺帧、总时长、幅度、削波、静音、重采样与采集起点；先用同一当前后端和相同规则对照。不能声称经过浏览器和编码的两份 PCM 必须逐字节相同。

若缺失主要来自启动或播放位置，对齐有效区间后重评；若确认采集代码缺陷，单独修复并重新冻结 B0，再评架构。不要把采音修复与 A1 一起记作“句级提交收益”。本轮不修改采音代码，也不获取测试视频。

| A1a：滚动识别 | 先离线因果模拟，再接入定稿协议下的滚动识别；原边界对照；解码/资源日志 | 日文信息与最终中文不劣于 B0-new，工程不变量全部通过；另记可用源文出现时刻 | 先修工程不变量；不带已知丢失/重复问题进入 A1b |

| A4：收口 | 未调参材料、Chrome、生命周期、离线启动与 60 分钟稳定性 | 给出保留/试用/替换默认的结论及证据 | 重要验收缺失则结论为未完成，不用开发集替代 |

### A0 收益上限计数

A1b 能改变的只有翻译单元的边界。动工前用现有 B0 记录和 9 段 PCM 数清三件事，全部只读、无需新模型：

1. Reazon 原始输出中带句末标点（`。？！`）的切片占比，决定“标点提前提交”是否存在。
2. 88 个 VAD 切片的时长分布，以及其中由最长语音限制而非 600 ms 停顿放行的占比。sherpa 的 4 秒限制是否硬截断没有核实，已有记录显示存在约 6 秒的段。
3. 34 项中当前未正确的项，有多少落在非停顿放行的边界上或跨越相邻切片。这是句级提交可恢复项数的上限；合并实验已覆盖其中间隔不超过 160 ms 的相邻对，结果为净减 2 项。

上限项数少于继续条件要求的净增数时，A1b 不进入实现，直接记录为“当前素材上无可验证收益”，等待用户提供的新材料。

### A1 继续条件

工程不变量必须全部通过。两轮 final 的确认关键语义均不新增错误，并满足以下任一条件：

1. 两轮 final 正确项相对同种子 B0-new 各净增至少 2 项，且 5 秒正确覆盖不下降。B0 自身两个种子相差 2 项（20/18），单轮净增 1 项落在这个波动内，不算收益；或
2. 仅当 A0 确认标点提前提交路径存在时适用：两轮 final 正确覆盖不下降，共同正确项的定稿延迟中位数至少改善 500 ms，尾部未出现新的超过 5 秒等待。没有该路径时本条在结构上不可达，不作为出口；或
3. final 正确覆盖不下降，可靠的日文候选在至少 3 个语义项上提前至少 500 ms，足以支持一个受限的 A2 草稿探针。此项只授予探针资格，不能声称用户已得到收益。

总分持平但存在一进一退时，必须逐项展示回退，不能称逐项非劣。新增已确认关键错不能用另一个恢复项抵消。待确认标签影响结论时做保守结果与敏感性分析，不升格为正式质量通过。

若第一次无收益，只允许针对 trace 中已定位的一个机制追加一次参数对照，例如 ASR 完成时间显示 800 ms tick 成为等待来源时测 400 ms。没有证据不同时扫描窗口、停顿和稳定轮数。

总的退出条件：**在同批音频上，滚动识别与句级提交若既没有稳定净恢复，也没有可靠提前，或其关键回退/计算开销抵消收益，应停下重新定位，不继续堆草稿、上下文和新模型。**

### A2 继续条件

先证明同输入 final 不因插入草稿而改变。相对 A1b，至少 3 个语义项的“持续正确且可读中文”提前，两轮共同项中位数改善达到 500 ms，5 秒正确可读覆盖不下降。

初始可读性目标为每行可见文本修订次数 P95 ≤ 3；仅 draft→final 状态变化且文字相同不计文字修订。报告错误草稿暴露时长，重点逐项检查否定、数字和主体翻转。用于默认采用的代表性验证中，不能出现满足可读时长的已确认关键错误草稿；若只有隐藏草稿才能满足要求，就保留 final-only。500 ms 与修订次数是起始门槛，修改必须发生在下一轮结果揭示前，并说明原因。

### 默认采用与发布

开发集的小收益只允许进入下一步，不自动替换默认。默认采用还需用户提供的未调参片段、真实 Chrome、资源、生命周期和长稳验证，且没有已知关键回退。

现行面向用户的质量目标仍保留为独立发布检查，例如句末 5 秒内正确覆盖 ≥90%、正确字幕 P50 ≤1.5 秒/P95 ≤3 秒、短句首次正确 P90 ≤4.5 秒；这些来自既有 [架构验收目标](architecture.md)，要在校准参考与足够样本上评估。本方案不通过降低发布目标来宣布原型已成熟。

只有 A1/A2 有结果后才安排本节。每项固定同一份源文与边界，避免把 ASR 随机变化混进 MT 对比。

| 对照 | 改动 | 必查问题 |

| T0 | 仅把当前温度 0.2 改为 0；其他采样与模板固定 | 旧切片上已测过：贪心 18/18、采样 20/18，无恢复（见第 2 节）。仅当 A1b 改变了翻译单元且被采用时重跑，回答新单元上结论是否不同；否则跳过并引用旧结果 |

| G1 | 仅对当前实际源文命中的预先冻结术语应用词表 | 未命中输入与控制一致；不能根据当前参考答案临时补词；保留自然未命中对照 |

上下文表现形式先选一种验证，多轮消息只是候选形式，不自动优于背景块。必须有对应的空上下文模板控制，区分模板变化与真实上下文收益。首配置仅使用过去已提交日文，是否添加历史中文另列实验，以免把旧误译持续带入。

新增上下文会增加 prompt 和推理成本。每次 final 的上下文快照固定，草稿不能因未来行完成而重翻过去 final。温度、上下文和词表不能一次性叠加后再猜收益来源；单项成功后最多做一次必要的组合确认。

不启动旧 P3 模型池。如果最后证据显示主要错误仍来自模型本身，先列出具体剩余错误类型，再单独决定是否重开模型探索。
