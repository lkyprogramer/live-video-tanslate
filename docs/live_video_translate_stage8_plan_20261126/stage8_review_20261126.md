# Stage 7 复核与 Stage 8 完整优化建议

2026-11-26，面向 M1 Pro / 32 GiB 日语视频→中文字幕。

审查对象：[当前 main：7ea1386](https://github.com/lkyprogramer/live-video-tanslate/commit/7ea13865c8c3673a1463495058a200723b153111)，包含 `3f901ca` 的 Stage 7 行为改动及 `7ea1386` 的验证归档。两次提交已经在远端，无需按 Gemini 文末再推送一遍。

## 结论

**Gemini 的“分开验证 ASR 与 MT、提高质量预算、保留 ANE 草稿”的方向有价值，但“已经达到模型天花板”“1.9 秒是日语物理下限”“MoE 可以保持 4B 延迟”三项结论均过强。**

Stage 7 有真实改善信号，也已经有很好的 ANE 低延迟基础。但是当前最有价值的下一步，不是先下载最大的模型，而是验证：剩余错误有多少来自缓存/模板、切分与字幕语义单元，有多少才是模型能力。否则换模型仍可能把同一类错误带入下一轮。

### 1. 哪些改善成立，哪些还不能作结论

归档有全集 CER `.4549→.3702`、前 5 分钟 `.4667→.3725` 的改善；但 Stage 6 从走到定稿/浏览器的片段取 ASR 文本，Stage 7 从 pre-MT ASR 取文本，全集 Stage 7 又是快速离线回放。它们是值得肯定的信号，**不是严格同口径的纯 ASR 因果收益**。

Stage 7 的终稿 `.696/1.056s`、首 delta `2.294/3.583s` 是前 5 分钟 WebSocket 回放结果；Stage 6 的 `.574/.919s` 是完整浏览器的 DOM 计时。不能直接用两个中位数相减，得出“更长上下文导致 +120ms”。更可比的同 654 条 Oracle-MT 中，P95 从约 `444ms` 增至 `702ms`，这值得专门消融，但 prompt 和上下文同时改变，还没隔离原因。

所谓“重度改写率 47.04%→31.07%”比较了首个通用文本 delta 与终稿，包含普通 token 追加。例如“今天”增长为“今天天气很好”并没有撤回已有内容，但编辑距离仍会很高。Stage 7 真实 `draft_sent` 只有 44 次，统计配对却有 103 条；必须先分开预览与终稿 token 流。

### 2. 这次源码审查新增的优先核查项（2026-11-26 本机已实测复现）

`local_pipeline.py` 手工构造下一轮的 `<|im_end|>`，而固定版本 `mlx-lm 0.31.3` 的 `generate_step` 在 yield 前有一步预计算（`L153: next_y, next_logprobs = _step(y)`）。**2026-11-26 已在本机 `Qwen3-4B-Instruct-2507-4bit`（`7ea1386`）实测复现：** 连续 4 轮对话后 `cache[0].offset` 相对 `canon_prompt_len + out_ids_len` 分别多出 **`+1, +2, +3, +4`**（即每轮多写入一个 `EOS 151645`）；且第 5 轮触发滑窗裁剪丢弃前两轮后，`迎えに来た親におかえりなさいって。` 的缓存译文退化为 `'回去跟来接你的父母说声“谢谢”。'`，而同 4 轮 fresh canonical 为 `'对来接孩子的家长说“欢迎回家”。'`。另外，清洗后的译文用于历史重放，不一定与缓存中未经清洗的 token 序列相同；`max_tokens` 用尽也不能视作正常 EOS。

因此该项已从“待复现疑点”升级为**已证实的 P0 修复项**（它解释了部分跨轮失真，仍不代表修复后 4B 就具备无限常识）。下一轮首要任务即记录逐 token ledger，修复 double-`<|im_end|>` 与 history 对齐并通过 cached vs fresh canonical 的 token/logits 一致性测试；修通并重建基线后，再评候选模型。

### 3. 更快和更准，分别从哪里来

| 目标 | 第一优先 | 条件升级 | 不应承诺 |
| --- | --- | --- | --- |
| 更早看懂 | 真实 DOM 可读首条、消融当前 1.6s 草稿下限/字符门槛、稳定前缀提交 | 自适应等待策略；后续日→中稳定前缀训练 | 任何句子都能 0.5s 得到不反转的完整译文 |
| 少听漏/断词 | 同 NeMo 的声学窗口与目标字幕区间分离、强切点右边界保护、输出归属去重 | 授权下载后用 Qwen A3（仅代码在仓）或 Turbo 选择性复核 | 把每条输入放长到 8s 就自动消除断词 |
| 少翻反/错常识 | 缓存正确性、成句输入、约束器与上下文消融 | 同底模 Q8；Index 2B 专用翻译；有预算再上 MoE | 参数大就一定更懂日剧，或者 Q8 必然提升 |
| 更低尾延迟 | 真实排队与 prefill/replay 分解、限制无效草稿、NeMo beam 热点 | 证据支持后优化 CPU beam / MLX 热路径 | 低平均占用意味着单条推理可再快十倍 |

当前代码实际采用 `min_speech_s=max(1.6,draft_interval_s)`，并附加最少日文字符数、增长量、句尾判断。这些是软件策略，不是日语语言学定律。日语句尾动词与否定确实会迫使部分句子等待，但不能把全体 `2.294s` 的 80% 宣布为不可优化。

### 4. 模型路线如何调整

1. **先不下载（G2）：** 仅用本机实际已有的 `Qwen3-4B-Instruct-2507-4bit` 修复已复现的 KV double-EOS 并验证缓存/模板与更短有效上下文；用已有 `NeMo-v2` 做同段窗口归因（注：`.model-cache/hub/` 已清理 `Qwen3-ASR-1.7B-8bit` 权重，仅仓库代码保留 `Qwen3AsrRecognizer` 适配，`Qwen3-ASR-1.7B-8bit` 移入需授权下载的 G3）。
2. **第一轮新候选（G3，零新 runtime 优先）：** MT 优先原生 MLX 路线——先用 `Qwen3-4B-Instruct-2507-8bit` 做量化归因，随后在内存与下载授权允许下对 `Qwen3-30B-A3B-Instruct-2507-4bit` 做 12–24 条成句难例首筛，只有质量显著胜出才做 4 路径延迟与 Chrome 共存 / swap 实测（绝不预设 `300–450ms`）。需要额外引入锁定版 `llama.cpp` sidecar 的 `Index-Translate-2B-GGUF` 降为第二梯队可选隔离挑战者（仅在 MLX 候选未达标且愿承担新 runtime 维护成本时启用）。
3. **ASR 挑战者：** 获下载授权后按 `Qwen3-ASR-1.7B-8bit`（复用仓内适配）与 `whisper-large-v3-turbo` / `kotoba-whisper-v2.0` 顺序同段盲测。
4. **不重复扫旧路线：** Qwen3-8B 已在同机测过，M0 P50/P95 约 `1.49/3.42s`；PLaMo 3 小模型也已失败。只有明确新输入/模板/运行时假设，才允许小范围重开。
5. **ASR 不盲目按参数排行：** Kotoba v2 是 756M；v2.2 主要增加后处理，不是新的 1.5B 识别模型。公开日语测试中，大模型在朗读与广播上的排名会反转，需用你的片源验证。

相近的 M1 Pro 14GPU/32GB 社区 oMLX 跑分中，30B-A3B Q4 为约 35.5–43.2 tok/s，1k 冷前缀 TTFT 约 3.27–3.49s。这不是你的短句热缓存成绩；它的意义是：**不能把 300–450ms 整句完成作为高配档设计前提。**

### 5. 什么时候才值得继续动底层

现有 NeMo 原生实现已经用 vDSP FFT、Accelerate SGEMV、固定 Core ML 桶与 beam predictor cache。下一步不是泛泛地“开启 ANE/NEON/加缓存”，而是记录 beam 触发率、候选展开/分配/排序时间、桶大小、GPU 等待和 MT prefill/replay 占比。

若 CPU beam 尾耗时确实占关键路径，再试内存池、前缀索引和批量 joint 计算；保持解码排序/合并/分数语义不变。若主要耗时是语义等待或 MT，继续把 ANE 的几十毫秒压缩一半，对上屏只会有小幅收益。所有收益都要落在同一条请求的关键路径，而不能把独立阶段的 P50 相加减。

### 6. 推荐的下一轮交付

按 [README](README.md) 的 G0→G5 运行：评测与正确性 → 当前模型消融 → 有限新候选 → 有条件合流 → 真 Chrome 长跑。每阶段都可独立拒绝，未过门限就停止，不要求把整套架构全做完。

**本轮目标不是宣称达到物理上限，而是在固定机器、模型预算、片源分布与质量要求下找到可复现的最佳折中。**只有 Stage 7 与候选在同一真实浏览器管线、独立留出集、稳定运行条件下对比，才能回答“能否顺畅追剧”。当前证据还不足以直接作出这个发布结论。

本报告和文档包属于审查与计划：所有新性能目标均为待验证门限，未执行目标 Mac 推理。完整固定来源见 [来源台账](09_sources_and_history.md)。
